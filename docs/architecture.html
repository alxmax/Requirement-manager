Core Model

Spec → Code → Gate → Map

Four moving parts, one invariant: the requirement file is always the source of truth. Code declares membership; the gate enforces it; the map makes everything visible.

One file per capability

Each thing your project does lives in one .md file — a requirement. YAML frontmatter carries machine-readable fields (id, status, depends_on, optional milestone). Prose sections carry human-readable intent, contract, and acceptance criteria.

Code declares membership

Source files tag their role with a one-line comment. The member list is discovered by scanning — never hand-maintained. Four roles exist: implements, tested-by, generated-from, validated-against.

Requirement File

The single source of truth

Plain Markdown: YAML frontmatter for machine reads, prose for humans. Nothing else restates the contract — code and docs reference the ID.

requirements/AUTH-LOGIN-001.md 
---
id:         AUTH-LOGIN-001
status:     confirmed
layer:      feature
owner:      auth-team
depends_on: [CORE-SESSION-002]
milestone:  v1.4    # optional — shows on the Roadmap tab
---

# User login

> WHY: users need to reach their own data securely.

## WHAT — Contract
- It shall accept an email + password and return a session token.
- It shall reject an unknown email with a generic error (no user enumeration).

## HOW — Acceptance
- Given a valid email/password, When login is called, Then a token is returned.
- Given an unknown email, When login is called, Then a generic error is returned.

## WHAT — Verify intent
- Should the token TTL be configurable per environment?  # open question for human reviewer

Commands

All 21 commands

One stdlib-only Python script. No installation, no dependencies. Seed it with cp; run it from the directory where requirements/ lives.

gate
The gate. Every tag resolves, every confirmed requirement has code, nothing drifted. Run before every commit and in CI.
--strict promotes warnings to errors · --json structured output · --since <ref> git-scoped scan (full-scan fallback + WARN on failure)
sync
Rescan + advance the drift baseline + regenerate the map in one step. --accept-drift re-baselines an edited confirmed/implemented contract; without it, sync refuses to silently re-baseline confirmed drift.
init
First-time bootstrap: scaffold requirements/ + .reqmapignore, draft requirements from existing code, build lock + map. Idempotent; never clobbers existing files.
map
Generate _map.md (4 Mermaid diagrams) + _map.json (graph) + _map.html (self-contained viewer). Reads TODO.md for the Roadmap tab. --check freshness gate — exits non-zero if committed map is stale.
site
Inject/refresh engine-owned regions (nav links + counts) into a presentation page; scaffolds one if absent. --attach <page> · --regions nav,stats · --diagram <rel> links an Excalidraw HTML.
next
"What should I work on?" — prioritised actionable buckets: orphans · needs tests · needs intent review · drafts to review. Read-only, always exit 0.
lint
Readability check on non-draft requirements: long sentences (>35 words), stacked conditions (≥3 and/or joins), missing Contract/Acceptance sections. --strict exits non-zero on errors.
show <ID>
Consolidated dossier for one requirement: contract, dependencies both directions, code members by role with file:line, open verify-intent questions, risk signals. Answers "where is X implemented?" in one command.
dupes
Flag requirement pairs with overlapping contracts (TF-IDF cosine, stdlib). Catches divergent re-implementations before they land. --threshold T overrides default 0.35.
health
Corpus coherence snapshot: % of requirements fully green (confirmed + member + tested + no open questions + not drifted). --json for CI badges.
confirm <ID>
Human validation step: flip a reviewed requirement to confirmed. Refuses if no implements: member exists; warns if no tested-by: is linked.
new AREA-NAME-NNN
Scaffold a new empty requirement from the built-in template. The requirement template is built into the engine — no template file needed.
scan
List which code belongs to which requirement. Shows member counts per capability with file paths.
draft
Draft requirements for untagged code and prose files (.py .js .ts .md .html and more). Existing files and membership tags are preserved.
plan
Read-only extraction plan: JSON capability map from legacy code without writing any .md files. Safe first pass before draft. Add --md-glob for prose discovery.
findings
Aggregate open "Verify intent" questions across all requirements into _findings.md. Accepts an AI-triage sidecar for a classified view.
review <ID?>
Emit a JSON review plan (intent, contract, acceptance, anchors) for all requirements or one — an AI-feed for advisory quality review. Read-only, writes nothing.
export
Emit just _map.json for an external front-end. --out PATH or --out - for stdout.
search "<query>"
Rank requirements by lexical relevance, most-relevant first — the same TF-IDF/cosine model dupes uses, and the same one the viewer's search box runs, so CLI and UI agree on what matches. --top caps the hit count. Below a calibrated floor it prints "no strong match" rather than a spurious first result.
coverage
List the source files carrying no implements: tag, grouped by directory — the code your registry does not trace. --json for machine output. Read-only: it reports, it never gates.
gen-integration
Regenerate tool_definition.json (the function-calling schema non-Claude assistants read) and the command table inside SKILL.universal.md from the COMMANDS registry — the CLI's single source of truth. Never hand-edit those two; gate fails when they drift from the registry.
Layer Model

Bus and feature

Two layers, like a factory's main bus and the machines that connect to it. The bus is defined once and shared; features compose the bus via depends_on.

layer: bus

Foundation

Shared capabilities with high fan-in: config loading, parsing, scanning, drift detection. Define the contract precisely — an underspecified bus is the most expensive thing to discover late. Change only behind the contract.

ARCH-PARSE-001 · ARCH-SCAN-002 · ARCH-DRIFT-003
layer: feature

Composed capability

Built on top of the bus via depends_on. Each feature has its own contract, acceptance criteria, and test coverage. Features can depend on each other but ultimately trace back to bus capabilities.

ARCH-CHECK-006 · ARCH-MAP-007 · ARCH-INIT-012
Split heuristic. If a requirement accumulates more than four or five acceptance criteria that cover behaviors which could break independently, it's a split candidate. Author two requirements, each with its own contract and its own failure mode. next flags these automatically.
Status Lifecycle

From draft to confirmed

Status controls what the gate enforces. Only confirmed requirements are treated as normative truth — everything else is descriptive or in-flight.

draft
Auto-extracted. Unreviewed. Gate ignores it.
→
baseline
Descriptive. Gate alerts only on change.
→
in-progress
Being built. Gate checks link sync.
→
confirmed
Human-validated. Gate enforces as truth.
→
deprecated
Retired. No longer enforced.

Errors → exit 1

  • Dangling tag: code points to a non-existent requirement
  • Orphan: a confirmed requirement has no implements: member
  • Bad depends_on: target requirement doesn't exist

Warnings → exit 0

  • Drift: contract changed but members not re-touched
  • Test-link: tested-by file has no test function
  • AC-coverage gap: labelled criteria without a verifies: tag
Use gate --strict to promote drift and test-link warnings to errors — useful in CI when the corpus is fully confirmed and the lock is current. Use gate --since <ref> to scope the gate to only requirements touched since a git ref (fail-open: falls back to full scan on git errors).
CI/CD

Wire the gate everywhere

Pre-commit hook for local enforcement. Published GitHub Action for the whole team. Both run the same reqmap.py gate under the hood.

Pre-commit hook

.git/hooks/pre-commit 
#!/bin/sh
python -X utf8 scripts/reqmap.py gate

One-time setup per developer clone. Blocks a commit on gate failure. Add --strict to also error on drift and broken test links. The pre-built hook lives at plugin/hooks/pre-commit.

GitHub Actions

.github/workflows/reqmap.yml 
name: reqmap gate
on: [push, pull_request]
permissions:
  contents: read
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: alxmax/requirement-manager/check@v1

Uses permissions: contents: read — least privilege, the gate only reads the tree. Inputs reqmap-path and working-directory adapt it to wherever you vendored the engine.

Secure deploy — OIDC, no stored secrets

.github/workflows/ci.yml — deploy-map job 
deploy-map:
  needs: gate-and-tests
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  permissions:            # least privilege, per job
    contents: read
    pages: write
    id-token: write       # mint the short-lived OIDC token
  environment: { name: github-pages }
  steps:
    - uses: actions/checkout@34e1148…        # pinned to commit SHA
    - uses: actions/configure-pages@983d773…
    - uses: actions/upload-pages-artifact@56afc60…
    - uses: actions/deploy-pages@d6db901…     # consumes the OIDC token

This repo dogfoods its own map: the published docs/ site deploys to GitHub Pages on every push to main, authenticated by a short-lived OIDC token — no long-lived secret or PAT. Permissions are scoped per job (the gate job gets only contents: read); every action is pinned to a 40-hex commit SHA, and .github/dependabot.yml keeps those pins fresh weekly.

The Viewer

Double-click to open

reqmap.py map produces requirements/_map.html — a self-contained React app with your graph inlined. No server, no npm, no install. Four tabs:

Map
Interactive graph explorer. Bus-layout ranks by dependency depth. Color-coded, selectable edges. Click to open the detail panel for any requirement.
Problems
Linter-style inbox of every open signal: errors, warnings, needs-review, cautions. Each row jumps to its spec.
Spec
One requirement rendered for reading: frontmatter → WHY → coverage strip → WHAT → HOW → WHERE → Risk.
Roadmap
Gantt chart from milestone: frontmatter and TODO.md items. Amber dashed bars for todos, solid bars for confirmed requirements.

/ plugin marketplace add alxmax/requirement-manager
/ plugin install requirement-manager@requirement-manager
